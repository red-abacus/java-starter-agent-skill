## Eval before

Selected skill: [java-spring-change](/Users/folea/Workspace/abac/deconstruct-java/.agents/skills/java-spring-change/SKILL.md). This changes delivery configuration for an existing application; bootstrap and review are not the primary workflows.

1. Keep ordinary verification in `ci.yml`, including PR checks, independent of live models. Add a focused `ai-evals.yml` triggered **only by pushes to `main`**. Check out that event’s exact SHA and invoke the existing repository evaluation command with its existing credentials configuration. Do not add live evaluations to PR, scheduled, or manual CI triggers.
2. Preserve local, on-demand use of the same command and configuration. Document prerequisites and result interpretation without changing application code, prompts, provider, or model.
3. Retain image publication after merges into `main`. Verify the resulting revision, publish its image, and record its source SHA and immutable digest. Image publication can proceed separately from evaluations; deployment requires both.
4. Put a mandatory gate immediately before Helm deployment in **every actual deployment entry point**. Resolve the selected image digest to its source SHA and require successful evaluation evidence for that SHA and the recorded configuration. Across separate workflows, query or consume trusted run evidence explicitly; a job-level `needs` dependency cannot connect workflows. Do not accept the latest successful evaluation from another revision.
5. Record the evaluation run identity, source SHA, model, prompt revision, dataset revision, generation settings, grader configuration, acceptance results, and execution status. Use approved evaluation data and keep credentials out of prompts and retained reports.
6. Treat quality failure, provider/infrastructure error, timeout, cancellation, skipping, missing evidence, and unavailable evaluation as deployment-blocking outcomes. Report quality failures separately from operational errors. If evaluation is still running, use a bounded wait or defer deployment; never interpret absence as success. Preserve diagnostics.
7. Continue the existing digest-based Helm release path after the gate. Serialize deployments to the same release, use bounded rollout and smoke checks, and apply the project’s recovery policy when release verification fails.

Verification before implementation handoff should demonstrate:

- PR and scheduled events cannot invoke live evaluations; a `main` push invokes the existing command for its event SHA.
- Deployment accepts matching passing evidence and rejects mismatched SHA/configuration, failed, skipped, canceled, missing, or unavailable evidence.
- Alternate deployment triggers and reruns cannot bypass the gate.
- Image digest, evaluation evidence, and deployed revision remain traceable through promotion.
- Workflow permissions, existing credentials, pinned actions, rollout checks, and diagnostics work at their actual boundaries.
